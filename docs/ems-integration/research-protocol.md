# EMS 协议独立核读与云端接入建议

日期：2026-09-27。只读研究；未改产品代码、未连接 Broker/EMS、未执行资料中的部署命令。完整分块阅读 `20260917/05_EMS与云端MQTT交互协议.md`（1001行，V0.5）及 `06_EMS故障与告警方案.md`（432行，V0.4），读取9份JSON参考（关联窗口的601行以程序解析检查）。下文“05 §…”、“06 §…”均指这两份资料；实现状态只是资料声明，未由现场运行证明。Kafka 为用户确认已有基础设施；以下 PG/CH 分工是建议设计，不表示现有服务已经具备。

## 1. 核心判断

接入可先做“身份与连接 → 原始接收 → 可靠业务保存/ACK → 状态投影 → SaaS读模型”，但不能把目标文档当成全部已实现。尤其不能把 MQTT PUBACK、Kafka 入队、当前告警、历史事件、人工处理状态混成一个成功状态。

建议以 PostgreSQL 作为告警事件、重要历史包和去重的事务性可靠保存点；同事务记录 ACK outbox 和供下游重建的数据。Kafka 承接削峰、异步派生及回放；ClickHouse 保存可重建的时序/分析投影。成功业务 ACK 在 PG 提交后生成，不等 CH 成功，也不能只因 MQTT 已收包或 Kafka 已入队就确认。若改成 Kafka 即最终可靠保存边界，必须另行证明对象内容冲突、去重状态、完整包保存和重放保留期的一致性，不能只给 `acks=all` 当证明。（05 §2.3、§5.3、§6.2）

## 2. Topic、身份、容量与连接

固定前缀 `ems/v1/{emsId}/`，MQTT 3.1.1；全部 retain=false，不用 QoS2。每台 EMS 一个连接。

| 后缀 | EMS方向 | QoS | 业务 |
| --- | --- | --- | --- |
| up/heartbeat | 发 | 0 | 双订阅就绪立即发，之后30秒；含 connectionId |
| up/status | 发 | 1 | connected/disconnected辅助提示 |
| up/response | 发 | 1 | 下行查询响应 |
| up/telemetry | 发 | 普通/单体0，结构1 | EMS、柜、单体、结构 |
| up/important | 发 | 1 | 仅重要历史补传 |
| up/alarm | 发 | 1 | alarm_event/alarm_data/alarm_current |
| down/request | 收 | 1 | 业务请求 |
| down/ack | 收 | 1 | 可靠保存确认 |

- `emsId` 是永久小写带连字符 UUIDv4，ClientID=emsId，与 SN/柜号不同；升级、IP、角色、证书续期不变。云端显式注册 EMS→租户/项目/站点，不能从载荷自注册归属。TLS 客户端证书唯一CN必须等于ClientID；Broker绑定证书/ClientID/Topic权限；有载荷emsId时也必须一致。（05 §2.1–2.3）
- 正式为mTLS TLS1.2/1.3；固定IP连接需匹配IP SAN。资料的120.27.23.229:1883并未证明支持TLS，正式端口仍待定。显式tcp只供受控联调，当前EMS未实现用户名密码认证。（05 §2.2、B.2）
- CleanSession=true，无LWT，每次连接重新精确订阅两个down Topic，均成功才就绪；不依赖Broker离线会话。cloud订阅telemetry/alarm需请求QoS1，避免结构降级。
- 每次连接生成新`connectionId`；心跳 `{v:1,emsId,connectionId,uptimeSeconds}`。90秒无新心跳仅代表通信不可达，不等于设备停机/故障；uptime是云通信线程时长，不是开机时长。status无connectionId，仅辅助，不能覆盖新连接状态。重放历史心跳不得续云端在线时间。（05 §2.3、B.3）
- 完整紧凑UTF-8正文：普通/单体/告警事件/清单/历史包≤6144字节，structure及含外层响应≤65536，alarm_data≤131072，下行≤4096。Broker、桥接、Kafka、应用解析均须覆盖最大类型并限制速率；不能一刀切6KiB，也不能靠截断列表通过。（05 §2.5、B.4）
- topic不提供跨业务完成顺序保证。即使Kafka按emsId分区，也仍须用connectionId/seq判现状，不能假设多个Topic或多实例桥接天然全序。

## 3. 上行信封和质量语义

| 类型 | 必要结构 | 含义/存储注意 |
| --- | --- | --- |
| ems | `{v,type,d:{base:[{ts,q,p}],cfg:{rev,p}}}` | 每60秒完整；base按来源分块；cfg173项与rev同快照，9项预留null |
| cabinet_30s/60s | `{v,type,c,d:{emu,bms,tms,pvdc,pcs,grid}}`，块为`{ts,q,p}` | 每柜分别完整；241/54点，共295；30s另有link:{ts,online} |
| cell_voltage/temperature | `{v,type,c,sv,d:{ts,q,values}}` | 每柜各60秒完整二维数组；BMU/位置不可压缩 |
| structure | `{v,type,connectionId,seq,sv,d:{ems,publicMeters,clusters,clusterLayout}}` | 变化触发，非周期；快照现状与布局分开 |
| alarm_event | `{v,type,sv,alarmId,seq,device:{c,type,id},code,level,state,ts}` | 事件去重emsId+alarmId+seq；当前阶段sv=null |
| alarm_current | `{v,type,connectionId,c,seq,alarms}` | 清单根seq与内嵌事件seq不同；alarms条目保留事件原始字段 |
| alarm_data | `{v,type,sv,alarmId,start,step,points,data}` | 关联首次事件；每过程一份；seq不在本体 |
| important_history | `{v,type,taskId,c,part,parts,ts,p,data}` | 每data行 `[非负毫秒偏移,p索引,值]` |

上述业务上行正文不擅自增加emsId；身份来自Topic。历史/普通的点位列表均按pointId解析，不按位置猜点号。（05 §3–6）

- 保留数值0与JSON null；不使用字符串null。物理量已是工程值，云端不可再次寄存器缩放。版本点是字符串，20062是源顺序4个U16数组或整体null，不转成浮点64位数。（05 §3.1、3.3）
- `ts`是源观测时间或null；历史`ts+offset`是归档时间，不能和实时观测时间合并去重。另存cloud_received_at/ingested_at，不能补成源时间。q=valid/stale/invalid不等于健康、安全或字段完整率；可有valid块内个别null。（05 §3.2–3.4、6.2）
- EMS资源90005/6/7是CPU%、内存%、开机整秒；源年龄≥3000ms整块null/invalid；未映射90002/3/4保持null。cfg106单位、运行状态/功率来源枚举仍待确认。
- 单体已知布局整组无效：values=null、q=invalid，有旧真实ts则保留；个别位置null保留位置。不用空数组/人为全null阵列冒充已采集。未知sv跳过依赖结构的单体解析并查询，恢复后只处理后续普通数据，不要求补漏。可审计存原始包，但不能拿后来布局静默回填解释。（05 §3.4–3.5）
- 结构的null电表列表=未知，[]=确认未安装。state=pending_activation/active/exited不是在线；cellReady只表示结构核验，不表示实时值有效。SN、厂家、软件版本与设备位置分别保留，BMS逻辑分组不可造硬件SN。（05 §3.5）

## 4. 三种版本/序号域与现状投影

`cfg.rev`是生效配置版本；`sv`是EMS内设备结构版本；`connectionId+seq`是本连接的快照新旧。三者不能互代。

结构sv首次可信为1，未知null；实际布局/柜清单/电表配置变化递增，重连、数据变化、仅就绪、厂家/SN/软件版本变化不递增。结构快照seq在每连接从1开始，sv或d任何内容变化递增；推送与查询同一快照。同seq必须同内容；较小不覆盖。重连清空现状可信标志但可保留历史布局+sv，不能沿用旧state/cellReady。（05 §3.5）

清单seq按EMS+柜+连接独立从1；只接受当前心跳连接，较大更新；相同序号比内容；旧序号不得覆盖。新连接先unknown；更大seq的alarms=null令现状未知，不制造cleared或恢复通知。alarms=[]才是已确认无活动告警。事件存档独立：合法新事件触发本柜刷新需求，重复事件不再触发；旧事件不能直接改变现状。（05 §4.2）

建议PG维护连接表、结构快照表、结构版本布局表、按柜清单表、事件账本和刷新需求表；按emsId的连接epoch和expected_seq作条件更新，事务内更新投影与刷新代次。事件到来时增加refresh_generation；查询发起记录generation，返回只能完成所覆盖代次，期间新事件保留下一次刷新。null清单也完成刷新；临时失败受控重试；永久错误暂停。心跳前到达的快照有界暂存/查询，不能默认认作当前。（05 §3.5、4.2）

新增连接、Broker会话顺序、Kafka积压恢复需要明确：connectionId是随机UUID，无法按UUID排序；不能让迟到/重放的旧连接心跳把连接切回。建议在实时入口保存Broker接收顺序/会话信息或每EMS串行入口epoch，业务重放不更新实时连接。资料尚未提供心跳单调序号/发出时间，需双方确认入口权威和旧连接淘汰规则。

## 5. 可靠对象、ACK、冲突

| 对象 | 业务唯一身份 | 成功ACK（Topic提供emsId） |
| --- | --- | --- |
| alarm_event | emsId+alarmId+seq | `{v:1,type:"alarm_event",alarmId,seq}` |
| alarm_data | emsId+alarmId | `{v:1,type:"alarm_data",alarmId,seq:null}` |
| important_history包 | emsId+taskId+part | `{v:1,type:"important_history",taskId,part}` |
| 历史样本 | emsId+c+pointId+原归档时间 | 不单独ACK；包内任意样本冲突则整包rejected |

成功ACK无ok、无connectionId；失败在上述四字段加`error:"busy"|"rejected"`。普通、结构、单体、清单、心跳不发业务ACK。ACK不表示人工已处理、设备恢复、任务全部完成。（05 §2.3、5.3、6.2）

建议PG事务：校验整个对象 → 查唯一身份及语义内容摘要 → 原子保存完整对象、去重记录、下游outbox、ACK outbox → commit后发布ACK。同身份同内容再ACK且不重复业务；不同内容保留冲突证据并rejected，不覆盖。历史包需整包校验100行/6KiB、索引/值类型、parts一致性及跨任务样本冲突，任何失败不能写半包后成功ACK。canonical内容比较应保留数组顺序、数值精度、null、所有业务字段，避免原始JSON空白/键顺序造成假冲突；此语义比较在请求已有明确规定，上行业务对象具体规范可双方冻结。

PG已提交而ACK发送失败：outbox重试。Kafka消费重放：PG唯一身份再次命中，再发合法ACK；可靠数据不依赖CH恰好此时可用。CH消费重放必须有稳定记录ID和可验证去重/查询策略，不能把某种后台合并当作立即唯一。Kafka→PG偏移提交在PG事务成功之后；崩溃重放通过业务去重恢复。对重复ACK可合并待发送行，但不要永久抑制设备后续重试需要的重新ACK。

EMS行为：业务等待10秒，自MQTT库通知发送成功起算；最多追加3次（总4次），后暂停60秒；busy立即结束等待、暂停60秒；rejected暂停待修正。成功/失败先于发送通知仍生效，后续通知不能复活计时。告警现阶段4事件并发；历史同EMS跨柜只等待1包，≤5包/秒且≤16KiB/秒，重试也计额度。（05 §5.1、5.3、6.2）

## 6. 告警字典、关联数据与补传边界

06的181个候选码不是已启用/验收的故障种类。统一码是6位大写HEX，高8位系统、低16位类型，000000不分配。code不是pointId，level=1/2/3/null；device.c为1..30或公共/EMS本机null，device.id位置必填可null。只按确认适配profile解释，vendor标签不自动选厂家驱动。云端不应对普通故障字重新猜测生成第二套EMS告警。（06 §2–4）

发生、等级变化、恢复同alarmId seq递增，恢复保留恢复前level，再次发生新alarmId。源失效/预留码/断线不是恢复。汇总、明细、安全事件分计；异常设备按同一层级去重。BMS20062高低字节映射必须保留，TMS厂家分支、酷特安极性、同飞循环码都不能用“非零即故障/换码即恢复”。profile变更不得重释历史。（06 §3、5–7）

alarm_data以首次T0为中心前后各5分钟，step=1000、最多10点；T0+5分钟且可读即从RAM提取并可靠保存，不等网络/ACK。首次事件seq1成功ACK后才传；自身ACK后释放。1秒取样不等于每秒新测量，缺口保留位置null，不插值/删行。样例601行含两端点；非网格T0对齐、正式点号/单位/精度、保存和恢复未冻结，900001/2是占位。当前在线告警阶段明确不实现alarm_data。（05 §5.1、5.3）

重要补传只覆盖EMS检测MQTT断线起至重连双订阅就绪止，不覆盖在线云端未保存或断线被检测前在途缺口。114点：60点由10s档取固定30s桶最后真实记录；14电量点保留60s档；40变化点保留变化并加各点异常起点前最近一条参考。区间左闭右开，首尾桶取交集；无行不造null。仅SSD，不读/追踪spool，不回扫晚到数据。（05 §6.1–6.2）

taskId重启固定；全部选数分包后固定parts才发送，每包≤100行且≤6144B。原包不能因源清理/新增而重打包；不可重建则暂停。现有INT64→double历史链可能已损坏20062低位，输出改数组无法修复已丢精度。云端不声称补传完整，也不能从part/parts推断断网区间或完整率：正文没有任务区间、缺口、点位覆盖清单；这要补充任务摘要契约或界面明确“已接收包进度”。（05 §6.2、7）

## 7. 下行现在能做什么

正式新请求仅 `structure.get`（params={}）与 `alarm.current.get`（params={c:已分配1..30}），信封严格为 `{v,emsId,connectionId,id,op,expiresAtMs,params}`，QoS1非retain；id=1..64 ASCII字母数字-_，新请求推荐UUID。成功响应 `{v,emsId,id,ok:true,data:完整对象}`，失败 `{v,emsId,id,ok:false,error:{code,message}}`。按code判断。兼容旧communication.status.get不要求connectionId/expiresAtMs、无去重缓存，不能用旧信封发新查询。（05 §2.4、4、B.3）

接收/执行前顺序：格式身份→当前连接→期限→幂等→业务。默认30s绝对截止，当前时间等于截止即过期，整数十进制准确比较。只读时钟不可信例外不跳过字段/连接检查，队列单调时间≤5s。每连接32条/60s缓存，自首次受理计时不续期；同ID同内容回原结果，改变deadline也算不同内容；缓存满BUSY。断线不自动补发旧请求；不同连接清缓存。查询结果永久错误暂停，短暂失败用符合当前连接的新查询；不把查询重复ID当新的读回。（05 §2.4、4.1–4.2）

参数修改、启停、功率控制、复位、XML下发当前都未开放。SaaS可以规划统一command记录、权限/审计/批准和只读查询入口，但不能凭双向MQTT发写命令。后续逐柜XML及控制必须先冻结操作白名单、参数单位/范围、目标设备、配置前置版本、有效期、设备本地互锁、执行结果/超时/读回、重复与未知结果、冲突、回滚。业务ACK不能代替指令执行结果。（05 §1、2.4、7）

## 8. 实现声明冲突和资料样例陷阱

1. 05 §1说告警提供者“仍未接入”、合法查询DATA_UNAVAILABLE；B.3却说已接入43规则，来源未知null；§5.1/附录C又定义在线告警阶段。应索要实际EMS版本/commit、启用清单和现场抓包，不能选一句当验收结论。
2. 目标§5.1有断网/持续ACK超时后可靠保存，当前批准阶段仅4096紧凑RAM记录、4并发，同进程重连保留，重启不恢复、满队报告新增丢失；无alarm_data。不能给SaaS承诺“告警永不丢”。
3. 06仍待首批启用确认，181候选≠B.3的43规则；profile/字典版本尚未在事件中表达，历史解释如何冻结需另定。
4. §5.2阶段sv统一null，而事件JSON样例sv=1：样例只演示目标格式，不能用其断言运行携sv。
5. 单体参考为5×32电压、5×16温度、sv=1；结构参考却为5×52/26、sv=1。它们不能作为同一EMS的端到端一致联调fixture；须创建成对匹配的测试集或隔离EMS身份。
6. 电表样例均有一只，而当前实现三处电表列表应null；样例不证明已采集电表结构。参考UUID/时间/默认cfg均非现场。
7. 普通柜/单体、SSD补传、关联窗口等正文目标不能由“8 Topic已实现”推导已接入；正文明确EMS60、结构接入，其他能力须逐项取证。

| P1 | 历史宽位图无损链、固定包重建、任务区间/缺口报告、晚到记录接受边界 | 不承诺无法证明的补传完整 |

建议验收用例：重复对象再次ACK；同身份不同内容rejected且无半写；PG提交后进程死而ACK未发；CH不可用仍保留可回放数据；旧连接/旧seq/旧查询不得覆盖；清单null不恢复；查询途中新事件保留刷新；alarmData/event独立ACK；两任务同历史样本同值去重/不同值整包冲突；未知sv不解释单体；真实0/null/stale/版本字符串/4×U16无损；按类最大正文；EMS重启告警RAM缺口明确；云端单独重启先心跳再查询。

## 10. 规模估算输入（用于后续容量测算）

稳定上行每EMS每分钟：心跳2、EMS60报文1、每柜30s报文2+60s报文1+两种单体2，即 `3+5C` 条/分钟（不含结构变化、告警、响应与补传）。每柜普通点约 `241×2+54=536` 点值/分钟，单体另外V+T个/分钟；EMS配置173个/分钟但可按cfg.rev/内容压缩形成配置快照。30柜约153条/分钟/EMS只是消息量，不能用它替代单体展开行数、事件尖峰及历史积压测算。按在线EMS数、柜分布、实际BMU规模、保留天数和查询范围再确定Kafka分区、PG保留与CH分区；不凭样例文件大小给上线容量承诺。

## 11. 主任务回传的基础设施核查（本子任务未自行连接验证）

主任务在本报告编写期间回传只读现场证据：专用Mosquitto监听8883、mTLS证书含IP SAN 120.27.23.229，证书有效期2026-09-16至2027-09-16；旧1883是另一匿名Broker。因此资料中的“正式TLS端口待定”可由主任务核查结果推进确认，不能继续以1883代正式端口。仍需端到端握手/双设备负向验收。

其余直接阻塞：

- `use_username_as_clientid=true`会替换客户端ClientID，不能当成“错误ClientID被拒绝”的证据；正式协议要求CN/ClientID绑定，行为差异需明确接受或修正后验收。
- 当前云端身份仅被授权单EMS的heartbeat/response读取与request发布，没有telemetry/alarm/ack完整闭环权限；需为新接入路径定义专用最小权限账号，不能直接宣称云端具备6上行/2下行权限。
- payload限制65536、packet限制73728无法容纳128KiB alarm_data；上线关联数据前必须同时核算正文、MQTT头、Broker和客户端限制。
- Kafka3.9.1是单节点KRaft、SASL_SSL 127.0.0.1:19094，RF1/minISR1；默认保留72小时且每分区512MiB、默认3分区。字节阈值可能先于72小时截断，RF1不提供节点冗余。因此本方案更不能把“Kafka已接收”当终态业务ACK条件。
- Kafka元数据查询超时，当前broker-controller心跳超时；仅确认存在，不能称健康可接入。先独立诊断并完成读写验收，再将其纳入可靠路径。
- 旧telemetry/Flink/Redis链路已运行且关联其他数据库；新接入宜隔离Topic/消费者组/账号/数据域，并通过既有SaaS服务边界做有证据的读模型适配。此研究不授权修改旧服务。
