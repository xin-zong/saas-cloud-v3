# 角色权限加载缓慢修复

## 原因与调整

`superadmin@prototype.local` 可管理的首个组织有 20 个角色、180 条角色权限。旧角色列表逐个角色读取权限、逐个授权检查成员和站点，再逐项计算可分配权限。经 SSH 隧道访问数据库时，多次串行往返导致读取约 102.06 秒。

- 角色目录改为批量读取角色权限、可见成员数、可编辑及可删除状态。
- 权限目录及角色可分配状态共用批量可配置权限查询。
- 查询结果仅在当前调用中使用；写入仍按原逻辑在锁内重新校验所有受影响授权。
- 未修改业务数据、数据库表结构或前端布局。

## 验证

- 先运行查询次数回归，旧实现因超过 20 次 SQL 查询失败。
- 只读诊断使用真实开发库和该账号身份执行控制器查询，不创建登录令牌，也不通过 HTTP 绕过认证。
- 最终复测：20 个角色，9 次 SQL 查询，1.23 秒；权限目录 8 次 SQL 查询，0.83 秒。时间为本次开发环境实测，不代表固定性能承诺。
- `RoleManagementPostgresTest`：12 项通过，包含批量与原逐项逻辑对照，覆盖未来/已到期授权、禁用成员、组织边界、空归属和客户权限来源约束。
- 常规后端测试：43 项通过，54 项依赖显式数据库环境的测试跳过；上述数据库测试已单独执行。
- `role-permissions-api-ui.test.cjs`：8 项通过（浏览器、模拟 API 响应）。
- 打包成功，更新本地 18090 服务，`/api/health` 返回 UP。
- 临时测试 schema 内无剩余表，已删除空 schema。未操作旧业务库。

后端重启使内存登录会话失效，浏览器需要使用原账号重新登录。修复留在本地 `main` 工作区，未推送远端。
