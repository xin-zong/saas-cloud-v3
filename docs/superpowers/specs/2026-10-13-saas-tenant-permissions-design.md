# SaaS 租户与权限系统重构设计

状态：核心规则已由用户确认；业务代码、数据库和云端尚未改动。

需求来源：[EMS平台—SaaS权限架构需求 PRD](https://jcn5qienhs34.feishu.cn/wiki/AzTBwypgJiPck4k7aETc4Nz1nzd)。2026-10-13 登录飞书后逐节读取 1—6 正文，并查看 5.1 登录鉴权画板。基线提交：`1f77ca8dbc1f088fbf15aa68d653c8dfeb898305`。

## 1. 已确认的决策

1. 保留“角色授权绑定站点范围”；企业管理员覆盖本企业全部站点，包括以后新增的站点。
2. 第一版企业之间完全隔离，不提供安装商、服务商跨企业共享站点。
3. 平台统一维护预制角色，企业只读；更新实时生效，企业需要不同权限时创建自定义角色。
4. 待审批企业通过邮箱验证后的申请进度入口查询，不提前创建可访问业务系统的企业账号。
5. 邀请和欢迎邮件使用一次性激活链接，用户自行设置密码，不发送明文初始密码。
6. 一个邮箱只归属一个租户；Web/App 共用账号。邮箱规范化后在当前数据中心唯一。
7. 删除旧客户和组织模型、目录页面、接口、外键及组织继承鉴权，不在企业内保留旧组织树。

实施使用 Java 21、现有 Spring Boot/JDBC/Sa-Token、PostgreSQL、ClickHouse、React 19。不引入独立权限微服务。PostgreSQL 严格按三范式建表，所有关系具备外键、唯一性和必要 CHECK 约束。未获新指令前不执行云端数据删除或部署。

## 2. 当前模型的替换边界

- `organization` 不改名充当租户；新建 `tenant`，不保留组织递归授权。
- `customer` 不改名充当企业；企业资料独立建模。
- `app_user` 保留身份 ID、密码哈希和有效的个人配置；所属关系改为唯一租户。
- `app_role` 改为租户自定义角色，旧组织归属与组织内名称索引移除。
- `member_grant` 的逐条角色授权思想保留；旧组织、客户及已退休权限不直接搬入新角色。
- `member_grant_station` 保留“同条授权”的站点集合语义。空集合不代表全部站点。
- `GrantAuthorization`/`AccessControl` 的资源校验入口可以保留，内部实现替换。
- 不保留三类工作台身份作为权限或导航来源。企业类型是业务分类，不等于员工角色。
- 历史 Flyway SQL 不改写；通过新迁移完成扩展、迁移和最终清理。

## 3. 租户、管理员与电站

租户只有 `platform`、`enterprise` 两种类型。系统初始化一个平台租户；企业审批通过创建企业租户。企业类型 Installer/Distributor/Service Provider/Operator 使用多对多关联，不自动给予访问其他企业的权利。

每个租户有唯一受保护管理员关系 `tenant_administrator(tenant_id,user_id)`。该关系是管理员身份的唯一事实来源，不同时在用户表存 `is_super_admin` 或在普通授权中复制管理员身份。角色选择器投影展示其系统身份，普通角色授权接口不能授予、撤销或伪造该身份。管理员账号及系统身份不能删除、禁用；第一版不提供管理员转让入口。

企业管理员能力动态来自该企业有效权限包及企业端基础管理能力，不能取得平台菜单和跨租户权限。平台管理员拥有当前系统已实现且启用的全部平台能力；其他平台角色按配置生效。

站点拥有唯一企业租户和负责人。负责人只表示责任归属，不自动形成访问授权。普通员工以逐条授权绑定的站点为范围。企业管理员的新建站点覆盖由规则计算，不能依靠向授权关联表追加每个站点。

员工删除或禁用前，必须在同一事务内将其负责站点移交给本企业启用员工；候选人须有相应站点管理能力，无候选人时由受保护企业管理员兜底。不允许借移交改变站点租户，不允许把平台人员设为企业站点负责人。删除员工采用退出业务目录、撤销授权及禁止登录，保留审计和历史业务引用需要的身份行；旧客户、组织实体则在迁移收尾实际删除。

旧数据迁移的唯一待确认输入：现有合肥站、上海站、原型验证站及普通账号对应的新企业归属。已建议保留业务数据、统一归入“演示企业”，平台超级管理员归平台租户。该建议尚不能当作已确认映射；没有完整映射清单时，迁移程序必须停止，不默认全量授权、不删除站点或普通账号。

## 4. 有效权限计算

设某客户端全部已实现、启用且祖先启用的权限为 C；企业所有启用权限包覆盖的企业端菜单权限并集为 P；成员在资源 S 上有效授权的角色权限并集为 R(S)。

普通企业员工：`Effective(S) = C ∩ P ∩ R(S)`，并满足账号启用、邀请已激活、租户启用、资源属于本租户。

企业管理员：`Effective(S) = C ∩ P`，S 必须属于本企业；个人中心等基础能力不纳入 P。

平台普通员工：角色决定功能权限；访问企业资源还须有显式跨租户能力及目标业务操作权限。分别设 `tenant.data.read` 与 `tenant.data.write`，写权限不能替代读取等业务接口依赖，也不能由“平台租户”身份自动推导。平台审批专员不得因此获得电站数据。

- 多角色按同一资源取并集，严禁把授权 A 的操作权限与授权 B 的站点范围拼接。
- 租户管理操作不需要附带某个站点才能生效，取消旧客户管理依赖站点的规则。
- 菜单、父目录、角色模板、权限包禁用后，该来源贡献即时失效；其他有效来源仍可独立贡献相同能力。
- 移除权限包或禁用模板不删除原角色配置和授权历史；重新启用会重新计算能力，操作前展示影响并审计。
- 预制角色只有在企业启用权限包引用它时才能分配和贡献权限。模板变更动态计算，不向企业复制权限快照。
- 自定义角色只允许保存本企业套餐范围内已实现权限；套餐缩减后旧配置保留但不生效，界面只展示当前可配置项并说明存在套餐外失效配置。
- 授权开始时间包含、结束时间不包含；保留现有有效期语义，不添加 PRD 未要求的复杂委派链。
- 角色管理和成员授权管理不等于可以给自己升权。普通管理员只能配置或授予自身可委派的操作、站点和有效期；检查同一来源的范围，不跨授权拼接。企业受保护管理员的可委派上限是本企业套餐，平台受保护管理员的上限是当前实现的有效能力。事务内校验修改后的角色对已有成员的影响，禁止通过编辑共享角色绕过授权边界。
- 受保护管理员不能被普通角色管理接口降权；平台/企业管理员保护通过稳定身份关系判断，不根据名称或邮箱字符串判断。

## 5. 数据模型与约束

核心实体及关系（具体列长度在迁移中沿用现有合理约束）：

- `tenant`：ID、类型、启用状态、创建时间。企业名称放企业资料，平台名称来自平台配置，避免重复存储企业名称。
- `company_profile`：租户唯一外键、法定名称、国家/省州/城市/详细地址、选填系统规模、邮编、服务描述、商业注册号、税号、联系人、电话、官网。联系人与登录身份是独立业务事实；邮箱从管理员关联取得，不复制一份可冲突的登录邮箱。
- `company_type`、`tenant_company_type`；`business_scope`、`tenant_business_scope`；`company_tag`、`tenant_company_tag`：多选规范化。标签删除需清除所有关联并二次确认。
- `tenant_administrator`：租户主键外键、用户唯一外键；数据库约束该用户属于该租户。
- `app_user`：新增必填租户外键；规范化邮箱作为唯一登录标识；邀请中/启用/禁用/删除状态互斥，旧 enabled 及重复 email/account 状态最终统一，不保留可冲突的多套状态事实。
- `menu`：ID、父菜单、客户端、节点类型 directory/page/action、名称键、页面路径、权限码、一级适用端、同级排序、启用、备注及必要时间。父子同客户端、最大四级、禁止环，适用端从根节点派生。页面必须有已注册路由；操作节点对应已有后端权限码。
- `permission`：稳定接口操作码。目录节点不伪造可调用接口权限；非目录节点关联真实权限码，目录可用性由可见后代推导。界面文案从菜单字典读取，不重复维护两套业务名称。
- `permission_package`、`permission_package_menu`、`permission_package_company_type`：包信息、企业端一级菜单范围、适用类型。选中一级菜单涵盖其启用后代；Both 可选，Platform 不可选。
- `role_template`、`role_template_permission`、`permission_package_template`：平台预制企业角色及套餐引用，企业只读。模板权限自身也不得变成企业平台端权限。
- `app_role`、`role_permission`：租户自定义角色、权限集合。角色名称在同租户自定义角色内规范化唯一；允许与预制角色同名，以来源标签和 ID 区分。
- `tenant_package`：企业与套餐关联，联合主键；企业创建/变更必须至少保留一个分配包。所有已分配包都禁用时业务功能为空，但启用企业仍可进入个人中心，不伪装成有效套餐。
- `member_grant`：用户、租户自定义角色或全局模板二选一、有效期、实际授予人；两个真实外键加 XOR CHECK，不用缺乏外键的 `resource_type/resource_id` 存角色引用。
- `member_grant_station`：逐条授权与站点；角色、成员、站点须在同一企业，模板必须可用于该企业。跨行约束用事务服务及数据库约束触发器保证，不依赖前端传入租户。
- `company_application` 及申请类型/范围关联表：申请编号、提交表单、规范化邮箱、状态、提交时间；审批事件记录审批人、结论、原因及时间。申请是独立业务事实，不与批准后的企业资料双写同步。
- `email_challenge`、`account_activation`：用途、目标申请/账号、摘要、到期时间、使用/撤销状态。原始令牌不入数据库，不进入日志。
- `mail_delivery`：独立邮件投递队列，业务事件唯一幂等键、语言、发送状态、重试时间和必要错误。与 EMS `outbox` 分离；邮件激活信息使用受保护载荷，不以长期明文保存原始激活令牌。

站点保存租户外键；设备、测点、告警等已有必经站点关系的子数据，通过该关系校验租户，不机械复制 tenant_id。没有可确定租户归属路径的业务主体增加必要租户引用。所有同租户约束做成可验证的外键/触发器规则，禁止以应用约定代替约束。

审计记录实际行为的 actor、目标租户、动作、资源及发生时间；这是事件事实，不能用操作人当前所属关系反推历史目标。日志不记录密码、邮箱验证码或激活令牌。

## 6. 入驻、邀请和邮箱流程

注册保留 PRD 的企业资料、联系人和成功页三阶段。企业类型/业务范围多选、地址通过 Google Places 搜索及打点解析四级地址，系统规模选填。区分储能业务范围与自由文本服务描述，不沿用 PRD 中两个相同 Business Scope 字段键。

邮箱验证获得仅限当前邮箱申请操作的短期上下文；提交 Pending 申请后可查看申请编号、状态、时间线和拒绝原因，不授予任何业务权限。邮箱验证码设置次数、频率和有效期限制。相同邮箱存在 Pending、Approved 申请或已占用账号时拒绝重复申请；Rejected 可重新提交新申请，不覆盖原申请。

平台审批需要独立权限。按申请行加锁并检查 Pending：第一个提交生效，后续请求返回 409 已处理。Approve 在同一事务内创建企业、唯一管理员、套餐和欢迎邮件事件；不创建多份租户或多名管理员。Reject 要求原因，创建拒绝邮件事件。Approved 不可撤销，后续变更走企业管理。

审批通过和员工邀请发送一次性激活链接。链接只能打开设置密码页，不执行 GET 即激活；提交符合强度规则的密码后原子消费令牌并激活账号。邮件安全扫描访问链接不能提前消耗令牌。强度至少八位且含大小写字母和数字，沿用 BCrypt 实际字节上限；数据库只保存密码哈希。

重发邀请原子撤销旧激活令牌后产生新链接；已激活员工不能借“再次邀请”重置密码。链接只允许跳转当前数据中心配置的受信任前端地址。管理员激活前也不能登录业务页。

企业联系人编辑不改变不可编辑的管理员登录邮箱。显示名称通过个人中心更新，并刷新全局头像。

## 7. 会话、实时刷新与区域

保留现有登录限流、BCrypt 和已配置 TOTP，不因本次重构移除已有账号保护。

会话只认服务端解析的账号、租户和数据中心；不接受客户端任意 tenant_id 改变身份。平台查看企业的数据筛选必须经跨租户授权，审计仍保留平台真实身份。

权限修改提交事务后通知受影响用户刷新能力快照；后端下一请求始终使用当前授权，不等待前端通知。客户端断线重连、重新聚焦及定时校验作为补偿，不能仅靠浏览器定时刷新宣称实时生效。第一版不增加权限缓存版本字段，先使用实时权限重查与提交后事件。

员工禁用/删除、企业停用、修改密码要撤销全部设备会话。实时遥测订阅和权限刷新连接也立即关闭。角色/套餐收回关闭受影响资源订阅，其他功能正常保留。

数据中心是部署边界，不是首页地图筛选洲别。当前仅发布真实可用环境，其余地区不可选择；未来各数据中心独立域名、认证、PostgreSQL 和 ClickHouse，跨租户能力不等于跨数据中心能力。

## 8. API 与前端约定

保留业务接口路径和业务资源 ID；身份 DTO 替换旧 `role/organization` 展示依赖。新 `/auth/me` 返回 tenant、clientMenus、permissions、stationPermissions、administrator、可见基础能力；字段只包含当前启用功能，不暴露别的企业目录。

主要新接口族：

- `/api/public/environments`、`/api/public/registration/email-challenges`、`/api/public/company-applications`、`/api/public/company-applications/progress`：公开配置、邮箱验证、申请提交和验证后进度。
- `/api/public/activations/inspect`、`/api/public/activations/accept`：令牌检查与密码设置激活，令牌放请求体。
- `/api/platform/company-applications`、`/{id}/approve`、`/{id}/reject`：审批及明细。
- `/api/platform/menus`、`/permission-packages`、`/role-templates`：树、配置、排序、启停与影响预览。
- `/api/platform/companies`、`/{id}/packages`、`/{id}/status`、`/{id}/tags`：企业管理。
- `/api/company/profile`、`/people`、`/roles`、`/member-grants`：仅当前企业的资料、员工、角色和授权。
- `/api/me/profile`、`/password`、`/capabilities/events`：个人资料、密码和权限变更通知。

旧 `/platform/customers`、组织目录及组织成员变更接口退休，返回 410；不能映射到全局企业目录。旧组织权限码从可配置目录和运行时鉴权删除。原登录邮箱密码、MFA 和退出路径保留并替换内部身份模型。

前端用稳定路由键和菜单权限，不再根据中文名称或三种角色拼接导航。无权限页面统一 403 提示；权限撤销后退出该页并清理数据。个人中心保持可访问，不受套餐控制。

平台管理包含企业审批、套餐权限（包/菜单/预制角色）、企业管理、平台员工与角色及审计；企业端包含企业资料、员工、角色与站点授权。旧客户、组织树及临时组织授权入口移除，逐条角色站点授权入口保留。

Web 实现及 App 菜单权限树纳入本次范围；不新建原生 App。实际实施页面时必须重新读取对应 Figma 最新设计和截图，优先“克制风格”，记录新增流程的设计覆盖关系。本轮只分析 PRD，未声称已核对新页面 Figma。

## 9. 数据出口与异步任务

统一 TenantAccess 入口覆盖所有 01—08 控制器。列表按当前允许站点集合过滤；详情从持久化记录追溯站点/租户后检查，不能使用请求声明的归属。统计只基于授权数据，不能泄露企业总量。

ClickHouse 不负责员工/角色配置；查询前在 PostgreSQL 得到允许的点位、设备及绑定期间，CH 参数化限制到这些 ID。历史查询和分页途中重新检查授权，不依靠前端过滤结果。

分析任务、报告、下载及实时查询创建时验证权限；执行、结果读取和下载时再验证，权限收回不得继续提供文件。跨租户平台任务保留发起人及目标范围，不能用后台系统权限扩大范围。

## 10. 迁移、清理和验证

采用 expand → 显式映射与回填 → 新前后端协调切换 → 删除旧模型。执行前保存 PostgreSQL 可恢复备份、旧部署产物及映射报告；保持站点、设备、测点 ID 不变，避免破坏 ClickHouse 历史与 EMS 绑定。

最终删除 organization/customer 表、触发器、引用字段、旧有效组织视图、旧 user_role/user_station 历史快照及仅服务旧模型的代码。旧记录不再出现在运行系统；备份和审计是恢复及可追溯资料，不作为第二套运行权限。

先在隔离测试数据库验证外键、唯一性、四级树和同租户关系；负例必须直接 SQL 写入也失败。验证角色站点不可交叉组合、套餐禁用与多来源并集、模板实时更新、企业停用和全设备退出、审批并发与邮件重试、邀请重放、跨企业 ID 猜测、CH 历史、报告下载与 SSE 撤权。

首次业务验收至少建立两个企业及平台租户，证明第一版企业间完全隔离；不能仅在一个演示租户里验证后宣称多租户完成。模拟新企业数据必须明确标识；真实空数据保留空态。

切换后若已接受新的业务写入，回退前先冻结写入并核对新增记录，不盲目恢复旧备份覆盖新数据。云端发布端口继续 18085；执行发布需遵从届时用户指令。
