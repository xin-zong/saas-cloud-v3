# Individual member grants

All routes use `/api`; responses use the normal `{code,msg,data}` envelope. Grant DTOs use camelCase. None of these endpoints writes the legacy role/station link tables.

## Target and grant directories

- `GET /members?purpose=grants` is a minimal target picker authorized by `member.grant.manage` on the member's administrative owner and any non-null membership organization. It returns the existing snake_case basic fields `id,account,display_name,enabled,organization_id,management_organization_id`, without email. Default `GET /members` retains its existing `organization.member.read` authorization and fields.
- `GET /members/{memberId}/grants` accepts either `member.grant.manage` or `organization.member.read` across the target's administrative owner and non-null membership. Each row independently checks the role owner's branch and every selected station using the shared scope service. Grant inspection uses organization metadata scope and does not require the viewer to hold station capabilities or explicit station selections. Editing/revocation still require explicit selections through the full shared management scope check. Grant GET/options run in a read-only REPEATABLE READ request snapshot to keep authorization and returned metadata consistent under concurrent writes; this is not a session cache.
- Fully visible rows contain `id,roleId,roleName,stationIds,validFrom,validUntil,source,status,term,canEdit,canRevoke,canExpand,scopeRestricted,periodChangeRequired,reason,permissionCodes,rolePermissions,stations`. `rolePermissions` contains catalog descriptors `{code,name,module,scope,available,origin,reason}` for known codes; `permissionCodes` retains even unknown legacy codes. The `stations` field contains scoped `{id,name}` descriptors. This supports read-only role and station previews without opening the editable role directory or technical asset APIs.
- A restricted row contains only its grant ID and the restricted indication: `scopeRestricted=true,status=restricted`, false action flags, null role/time/source/term values and empty station/permission lists. The empty list here is redaction, never an editable or complete zero-station selection. No hidden station names, IDs, or counts are returned.
- `source` is `历史迁移` when the stored original issuer is null and `直接授权` otherwise. Edits preserve that original issuer; audits identify the actual editor. No issuer is fabricated for imported grants.
- `status` is `expired` at or after the exclusive end instant, otherwise `disabled` for a disabled recipient, `scheduled` before the start, or `active`. `restricted` is only a visibility placeholder. All timestamps are ISO-8601 UTC strings; authority comes from PostgreSQL time.

## Writes and terms

- `POST /members/{memberId}/grants` and `PUT /members/{memberId}/grants/{grantId}` accept exactly the grant fields `{roleId,stationIds,term}`. Required term values are `permanent|30d|90d|1y`. Station IDs must be unique positive IDs.
- Both return the saved grant DTO. `DELETE /members/{memberId}/grants/{grantId}` revokes that row and returns `data:null`. A missing or wrong-member grant returns 404. Repeat revocation returns 404 and does not create another audit.
- A role with any available station capability requires at least one station. Pure organization roles and empty roles may use `stationIds:[]`; organization scope comes from the role's owner branch and never implies all stations. New/expanded grants reject unknown or unavailable permission codes.
- An unchanged supported term preserves both original timestamps, even if stations or role change. An expired same-term grant stays expired. A changed term starts at the server's current time. `30d`/`90d` use fixed days; `1y` uses `Asia/Shanghai` calendar-year addition, including leap-day adjustment. Permanent means a null end.
- Terms are derived from the saved pair; there is no term column. Unsupported historical ranges return `term:custom,periodChangeRequired:true`. `custom` is display-only and cannot be sent on writes/options; the operator must explicitly select one of the four supported terms to restart. There is no automatic same-term renewal.
- `canExpand` is a catalog eligibility hint, not a promise of authority over arbitrary stations or terms. Existing unassignable roles can be retained while preserving/narrowing stations and preserving/shortening the interval. They cannot gain stations, change role, move the start earlier, or extend their end without normal available-code and delegation checks. A finite manager may safely narrow a permanent existing grant without deriving its existing lifetime again. Full old/new scope checks and governance preservation still apply.
- All mutations acquire shared advisory transaction lock `78291001` before mutable authorization reads and use `GovernanceGuard.snapshot/preserve`. Target administrative owner and current membership, old and new role owner, and every old/new station are checked. New capabilities use `GrantDelegation.requireDelegation`, including the same-source-grant hybrid `customer.manage` branch condition and source expiry bounds. Self-grant mutations are conservatively disallowed. Other administrators cannot remove/shorten the last complete governance horizon.
- Audits are structured `member.grant.create`, `member.grant.edit`, `member.grant.revoke` events with `memberId,before,after`. Mutation and audit share one transaction; a rejection rolls both back.
- Legacy `PUT /members/{id}/grants` still returns 410 with the individual-workflow hint. No full-set overwrite exists.

## Station options and authoritative preview

`GET /members/{memberId}/grant-options?roleId=112&term=30d&grantId=122` requires grant management; omit `grantId` for creation. An edit must supply `grantId`. Ownership and the entire existing grant are revalidated; outside-scope grants cannot be probed through options.

Response data is `{roleId,grantId,term,validFrom,validUntil,stationSelectionRequired,canSaveWithoutStations,canExpand,reason,stations:[{id,name,selectable,reason}]}`. Candidates are the actor's active explicit stations within management scope. Station eligibility uses the exact save validator for the selected role and proposed interval, independently of `asset.read`. Disabled candidates include an explanation; outside-scope candidates are omitted. For pure organization/empty roles, `canSaveWithoutStations` reports whether the zero-station assignment is currently permitted and `reason` explains a refusal.

With an unchanged term and existing grant ID, preview returns the original timestamps and evaluates remaining validity, so a grant with ten days remaining does not incorrectly require thirty new days. A changed term previews the server-calculated new range. The final save always revalidates and recalculates a changed period; preview is not an authorization token. The UI should show the returned end timestamp and use `stationSelectionRequired` rather than forcing a station on organization-only assignments.

## Verification and cutover

`MemberGrantPostgresTest` is opt-in under `EMS_TEST_SCHEMA=ems_permission_tests`, using the same guarded isolated database fixture as the role-management tests. Ordinary tests roll back all data/DDL. Its real concurrent revoke case commits only the dedicated isolated fixture, uses real Spring transaction proxies and observes advisory-lock contention, then removes the fixed schema-qualified allowlist. It must only be run with privately supplied test connection settings.

The catalog now marks `member.grant.manage` available because this endpoint enforces it. No migration or existing account grant is added. Apply the already documented coordinated schema/backend/client cutover; existing-account governance initialization remains a separate explicit choice.
