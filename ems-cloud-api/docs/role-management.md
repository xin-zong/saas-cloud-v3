# Role management and reusable governance contracts

All paths below have the `/api` prefix. New JSON fields use camelCase.

- `GET /platform/permissions?organizationId=` returns catalog items `code,name,module,scope,available,origin,configurable,reason`. Read access accepts `role.manage` or `member.grant.manage` on the selected organization. `configurable` additionally requires role management and an existing delegable capability. Unavailable entries remain visible with an explanation; only `role.manage` becomes newly available in this task. Member grant creation remains unavailable until its own endpoint is implemented.
- `GET /platform/roles?purpose=manage|assign&organizationId=` returns the selected organization's role definitions, including roles the actor does not personally hold. Default purpose is `manage`, requiring `role.manage`; `assign` requires `member.grant.manage`. Records contain `id,code,name,description,organizationId,permissionCodes,memberCount,canEdit,canDelete,canAssign,reason`.
- `POST /platform/roles` accepts `{name,description,organizationId?}` and returns an empty-permission role DTO. Supplying `permissionCodes`, including an empty array or explicit null, is rejected. Codes are server-generated, stable opaque identifiers.
- `PUT /platform/roles/{id}` accepts `{name,description}` and returns the role DTO.
- `PUT /platform/roles/{id}/permissions` accepts `{permissionCodes:[...]}` as the complete desired set and returns the role DTO. Duplicate codes normalize to a set. Unknown/new unavailable codes fail; existing unavailable codes may remain or be removed.
- `DELETE /platform/roles/{id}` returns null data. Any retained grant reference, including expired or disabled recipients, blocks deletion with 409. The message gives only the visible member count.
- `GET /platform/organizations?purpose=roles|grants` uses role or member-grant management scope respectively and preserves the existing `id,name,parent_id` shape. Omitting purpose retains `organization.member.read` behavior.

If `organizationId` is omitted, the directory prefers the actor's administrative owner only when that organization is permitted for the requested purpose. Otherwise it selects the numerically first authorized organization. It never defaults to global visibility and does not reject a child-only manager whose own administrative owner is higher. Clients should send the explicitly selected organization thereafter. Role names are trimmed, nonempty, at most 120 characters and unique within their owning organization.

`memberCount` counts distinct retained recipients whose administrative owner and non-null current membership are both visible for the directory purpose. It is not a count of all out-of-scope references. `canDelete=false` can therefore accompany zero visible members. `canEdit` also checks every affected retained recipient and station; an inaccessible recipient never appears in the response. `canAssign` is role-level eligibility only, based on available codes and the actor's organization/station capability upper bound. Individual grant saves must revalidate the chosen member, stations and interval. Unassignable roles remain in the assign directory with a safe reason.

## Mutation sequence for later grant/member/organization work

`GovernanceGuard` and `GrantDelegation` are reusable plain services constructed with the same transaction-bound `JdbcTemplate` and `GrantAuthorization`/`AccessControl`. They do not open their own transactions. Callers must use one Spring `@Transactional` method (default READ COMMITTED) for this whole sequence:

1. `GovernanceGuard.lock()` acquires advisory transaction lock **78291001**, shared with organization writes. Acquire it before reading mutable authorization or affected grants.
2. Recheck actor identity, requested management permission and all affected scopes. `GrantDelegation.requireScope(owner,member,stations,managementPermission)` checks the role owner, recipient administrative owner, non-null membership, each station's organization, and the actor's explicit active station selections. Use `requireMemberScope` for member-only changes.
3. For new capabilities call `requireDelegation(owner,member,stations,codes,validUntil,managementPermission)`. It requires active same-grant code/resource capability covering the target end instant, and management authority covering that end across the affected organizations. An indefinite target requires indefinite source paths. A future target still requires currently active authority lasting until its end. Past elapsed access is not reauthorized; expired targets have no remaining interval, but their retained scopes are still checked. Disabled recipients do not bypass these checks. Organization capabilities cover the role owner's descendant branch; current membership never determines their reach.
4. Save `GovernanceGuard.snapshot()` before mutation, mutate, then call `preserve(before)` before auditing/commit. Throwing must roll back both the business mutation and its audit. Snapshot/preserve must use the same transaction and lock. Future grant endpoints must validate input start/end ordering separately.

The hybrid `customer.manage` capability has an additional source condition in both role eligibility and authoritative delegation: the **same source grant** must contain the permission and station, and that grant's role-owner branch must contain the station's organization. Independent role-management authority or another grant's organization branch cannot supply this condition. The same source grant must also satisfy the target expiry bound. Other station capabilities retain their existing permission-plus-explicit-station semantics.

The snapshot computes complete governance for each organization: the **same enabled user** needs active `role.manage` AND `member.grant.manage`, which may come from separate compatible grants. Per-code expiry is the latest active source expiry; that user's complete horizon is the earlier of the two, and the organization's horizon is the latest complete user horizon. The guard preserves every previously present horizon, including indefinite governance. It does not require an existing governor where none was present, and never bootstraps accounts. New ancestor hierarchy changes must use the same guard sequence because they can change descendant scope.

Role permission additions check all retained grants, not only the active view. Removal-only edits need manageable affected scopes, but do not require possession of removed codes. Permission diffs and role metadata changes are audited as structured JSON. V9 registers only the `role.manage` permission code through `database/apply.sql`; it assigns no role or member. Existing accounts still require the explicitly chosen initialization procedure.
