# 储能电站管理后端：范围与架构提案

日期：2026-09-23。状态：用户已确认，实施中。

用户追加约束：创建新库，不使用老库。新库名称为 PostgreSQL `ems_cloud_v2_proto`、ClickHouse `ems_cloud_v2_proto_telemetry`；所有迁移和验证仅针对新库。

## 依据与目标

现有 `ems-cloud-ui` 是 React 原型；`ems-cloud-api` 原为空目录。以 `src/App.tsx`、`src/auth/roles.ts`、生产组件及 `docs/operations-data.md`、`docs/maintenance-data.md` 为依据，保留页面布局，将前端演示登录、本地保存和数据读取逐步替换为真实 API。

本期围绕既有电站。排除新站接入流程、EMS/SCADA 协议、真实设备控制、固件升级执行、市场交易接口和付款执行。相关页面仍支持记录查询、内部草稿和管理动作，但不能把保存或审批通过标记成设备执行成功。

## 技术方案比较

1. 推荐裁剪 RuoYi-Vue-Plus 后端：复用认证、授权、校验、审计等基础能力，采用模块化单体。其官方仓库支持 PostgreSQL；保留许可证与上游来源，实施时锁定经过兼容性检查的稳定标签。移除不需要的演示、代码生成、工作流引擎和分布式扩展；检查缓存依赖，若保留 Redis，应在部署清单明确说明。禁止直接照搬框架默认业务表结构。
2. 精简 Spring Boot 自建基础层：依赖更少、表结构更易严格控制，但认证、权限和审计需要自行实现与验证。如果框架裁剪会造成更多复杂度，选择此方案前说明差异。

保留现有 React 前端，不替换为脚手架 UI。不引入微服务、消息总线或通用流程平台。Java 环境已发现为 21；Maven、Docker 未在当前 PATH 检出，尚未确认数据库服务可用性。

## 数据库原则

PostgreSQL 是所有业务主数据、状态变更和授权的事实来源。严格按第三范式设计：字段原子化，多值关系使用关联表；非键字段依赖完整候选键；通过外键获取组织名称、设备型号信息等，不重复复制。设备测点能确定所属设备和电站时，不额外重复存储这些关系。

每张表设计时列出候选键、主键、字段语义、必要性与约束。使用 NOT NULL、UNIQUE、FOREIGN KEY、CHECK，按业务选择 RESTRICT 或仅从属明细 CASCADE。关系字段不使用逗号字符串或 JSON 数组；审批不使用无法建立外键的任意 type/id 指针。组织层级禁止环路；授权变更、审批和工单状态转换在事务中校验并处理并发冲突。

金额使用 NUMERIC/BigDecimal，功率与容量统一单位；SOC 限制 0–100，额定功率和容量为正，时段限制起止顺序及重叠。有效电价和计划时段优先用 PostgreSQL 排斥约束防止并发重叠。跨表功率上限等规则使用事务内校验；必要时用约束触发器，不能声称普通 CHECK 能覆盖跨表校验。

不默认添加通用备注、扩展字段、逻辑删除、租户编号、祖先路径或统计缓存字段。仅有业务用途时引入审计时间、操作者或版本。查询得到的收益合计和完整率不作为基础表的冗余字段。外部对账单金额与系统计算值语义不同，可各自保留。

ClickHouse 仅存时间序列事实，最小逻辑字段为测点标识、采样时间、值，以及确有来源的质量信息；不重复保存设备/电站/客户名称。它不支持外键，主键不保证唯一，因此不能宣称与 PostgreSQL 具有相同完整性保证。由受控写入验证测点，采用明确的重复采样策略，查询也必须保证每测点每时刻只有一个有效值。严禁用“最终会合并”代替重复数据正确性设计。当前阶段仅通过独立开发数据导入验证，不建设 EMS 接入链路。

若要求所有存储都必须由数据库强制外键与唯一约束，则该要求与 ClickHouse 的能力冲突，需要调整其用途后再实施。

## 接口与统计契约

- 接口按业务资源划分，统一分页、参数校验和错误响应；数据库实体与页面返回对象分离，避免把完整 Station 大对象直接存为 JSON。
- 后端校验操作权限和站点范围，包括详情、列表、汇总、导出及间接关联记录；不信任前端传入的角色或站点列表。
- 403 表示无权操作；状态或版本冲突返回 409；输入错误返回 400；服务依赖不可用明确报告失败，不返回演示成功。
- 时间存储带时区，业务日期初期统一 Asia/Shanghai；明确区间边界。正储能功率为放电、负值为充电，正电网功率为购电。
- 遵守现有数据文档：无数据不补零，不自动补演示曲线；显示覆盖范围；不同币种不混算；采样积分不冒充结算电表；未来实际数据不计入当前统计。
- 开发演示数据通过显式独立配置加载，生产不使用固定演示密码或固定动态验证码。

## 实施顺序与验收

1. 基础工程、数据库迁移、登录授权、既有站点/设备查询及前端接入，先形成可启动、可登录、可查真实持久化数据的完整链路。
2. 告警确认、工单与巡检状态转换、审批和审计，验证刷新及跨浏览器持久化。
3. 电价、策略计划、遥测历史、运营和收益核算，验证时段边界、重叠、空值和计算口径。
4. 市场记录、报告导出、平台管理和设置，核对所有原型可操作入口及权限矩阵。

每阶段更新接口文档、迁移脚本和页面能力清单。验收包括真实 PostgreSQL/ClickHouse 集成测试、违反约束的拒绝测试、跨站越权与并发状态转换测试，以及前端类型检查、构建和相关 UI 测试。无法运行的验证如实记录，不能以模拟数据库测试代替真实双库验证。

## 待用户确认的架构决策

建议采用裁剪的 RuoYi-Vue-Plus 模块化单体，PostgreSQL 承担严格三范式和关系约束，ClickHouse 仅承担受控历史事实查询；按以上顺序覆盖全部原型模块。审批中心在当前三个角色配置中均未开放，实施前需要明确可审批权限的授予方式，不能自行给所有服务商审批权。
