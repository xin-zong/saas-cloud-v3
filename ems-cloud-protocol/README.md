# EMS v1 wire protocol library

`new WireDecoder().decode(topic, payload)` accepts the six `ems/v1/{lowercase UUIDv4}/up/{channel}` channels and returns `WireMessage`. For heartbeat, status and response (which do not carry a wire `type`), the type discriminator is the channel name.

The library validates strict UTF-8/JSON, duplicate keys, trailing tokens, Unicode scalar strings/keys (including JSON escapes), topic/identity/type routing, required envelope fields, shapes and explicitly defined ranges. Unknown extension fields remain in the returned body and hash. JSON integers and decimal values retain exact precision; canonical SHA-256 sorts object keys, preserves array order and nulls, and normalizes mathematically equal numeric spellings. Under the 2026-09-28 capacity amendment, payload caps apply to received UTF-8 bytes: 64 KiB (65536 bytes) for all up messages and complete response envelopes, including alarm_current responses; alarm_data retains its 128 KiB (131072 byte) cap. Down/request remains 4096 bytes. The original V0.5 source fixtures and document remain historical evidence; EMS sender limits must be updated and cloud ingestion deployed before larger messages are enabled.

This is a normal Java 21 library using Spring Boot 3.5.15 dependency management, with no executable repackage plugin. Parsing limits are depth 64, number token length 1024 and string length 131072, in addition to payload size limits. Errors expose safe fixed messages without raw input or parser causes.

Envelope acceptance does not verify point catalog completeness or semantics, physical units, four-word point bitmaps, matching cell/structure layouts, assigned cabinet/device identity, current connection, snapshot order, quality freshness, alarm lifecycle, historical identity conflicts, durable storage or ACK timing. The typed interpreter below verifies the ordinary profile and cell dimensions. This module creates no transport, persistence, API or control behavior.

## Typed telemetry and source evidence

`PointCatalog.loadDefault()` loads the bundled, immutable `ems-v1-profile-20260917` evidence catalog. `find(namespace,id)` uses `cabinet`, `ems` and `config` namespaces. All 1,410 SQL records are retained in `cabinet`; the 295 ordinary wire points have `NUMBER`, `TEXT` (11 versions) or `U16_WORDS` (20062) rules, and the remaining 1,115 cell-slot/parameter definitions have `UNKNOWN` wire rules. `dcValueType/archivePolicy` are source evidence with unknown encoding semantics. They supply no scale, enum, read/write permission or wire type. Parameter 30115 is not a writable command. Units come only from explicit protocol text and appendix A.3, never name heuristics; unavailable units remain null. The referenced authoritative Modbus workbook was not supplied, so this profile does not claim complete semantic verification.

The 6 `ems` definitions are separate from 173 `config` ID references. EMS 90002/90003/90004 remain semantically unmapped. Configuration names are known only where the protocol states them (101/102); sample IDs are tagged reference evidence. `SCALAR` means permitted JSON scalar/null shape, with actual scalar type, enum and unit unspecified. It does not derive a numeric type from an example. Configuration control is not opened.

`new TelemetryDecoder(catalog).decode(message, layout)` accepts only ems, cabinet_30s/60s and cell_voltage/temperature. Complete ordinary frames are required by §3.2/3.3: 241 or 54 cabinet points in their reference placement, all 6 known EMS points, and all 173 known configuration IDs. Missing values must be explicit null, not omitted. The frozen cabinet profile rejects unknown IDs and misplaced points. §3.2 explicitly permits EMS extensions, so unknown EMS base IDs are skipped in observations while the raw `WireMessage` retains them. All legal received configuration scalar/null entries, including extension IDs, are retained separately under `cfg.rev`; arrays are rejected. Revision and structure version remain arbitrary precision integers. Source timestamps preserve null and reject values outside Java `long` rather than truncate.

`StructureLayout.fromMessage(structure)` accepts a direct validated structure message and preserves EMS identity, sv, connectionId, seq, cabinet state/readiness and BMU dimensions. The caller must supply a snapshot already accepted for the current connection; this library does not arbitrate heartbeat connections or sequence ordering. Cells require the same EMS/sv, an active ready cabinet, known BMU type/dimensions and matching matrix dimensions, with at most 500 positions per kind. Overall unavailable cells use `values=null,q=invalid`; individual null cells retain their positions. Empty/all-null matrices cannot replace an overall unavailable group (§3.4). No scaling, padding, physical bindings or invented cells occurs. Ordinary observations can parse without a layout and still require downstream asset binding before visibility.

`PointValue`, `ConfigurationSnapshot`, `CellFrame` and `TelemetryBatch` protect stored mutable JSON/collections with defensive copies. Observation/configuration/cell domains remain separate; no fake station or device IDs are added. Errors use fixed messages without raw bodies.

The offline `scripts/import-ems-catalog.py` takes explicit `--sql`, `--protocol`, `--references` and `--output` paths. It parses INSERT text without executing SQL, applies explicit protocol rules, rejects duplicates/malformed definitions, checks the complete ordinary profile and emits deterministic source hashes/counts. Runtime has no dependency on the source directory. `scripts/test_import_ems_catalog.py` verifies parsing, malformed/duplicate rejection, missing source rows, provenance, counts and deterministic hashes.

## Source fixtures

The nine JSON files under `src/test/resources/wire` are byte-for-byte copies of the independent reference files alongside `05_EMS与云端MQTT交互协议.md` in the supplied `20260917` materials. The protocol is SS-EMS-CLOUD-05 V0.5, SHA-256 `C00D096A3D4E418A5FCC411C51B03801132F657695E5DB5ECAE5540EC1D93E0D`. All examples are synthetic format references. The cell and structure examples describe different layouts; tests accept them independently and do not represent them as one consistent deployment.

`src/test/resources/telemetry/structure-matched-synthetic.json` is explicitly synthetic test data with 5×32/16 dimensions. It demonstrates matched parsing without altering or promoting the incompatible source references.

Tests additionally use the document's heartbeat/status/response and alarm_current forms, including legacy `communication.status.get` response shape. No down/request or down/ack decoding is supported by this interface.

Run from the repository root: `mvn -pl ems-cloud-protocol test` or `mvn test` for the complete reactor.
