# Independent ingestion worker

Java21 MQTT3.1.1 mTLS → Kafka worker; no API/web module dependency. Build protocol once with `mvn -f ems-cloud-protocol/pom.xml install`, then `mvn -f ems-cloud-ingestion/pom.xml package`. Execute the executable worker jar with managed environment configuration; do not place credentials in command arguments or source files.

Required environment: `EMS_DATABASE_URL`, `EMS_DATABASE_USER`, `EMS_DATABASE_PASSWORD`, `EMS_MQTT_CA`, `EMS_MQTT_CERT`, `EMS_MQTT_KEY`. MQTT key is PKCS8 PEM. Kafka properties path defaults to `/etc/ems-cloud-v3/kafka-client.properties` and supports Kafka FileConfigProvider. MQTT URI/client ID and Kafka lane topic overrides are `EMS_MQTT_URI`, `EMS_MQTT_CLIENT_ID`, `EMS_KAFKA_CONFIG`, `EMS_KAFKA_FAST_TOPIC`, `EMS_KAFKA_STATE_TOPIC`, `EMS_KAFKA_RELIABLE_TOPIC`. Queue capacity defaults256 per lane, lease30s (`EMS_QUEUE_CAPACITY`, `EMS_LEASE_SECONDS`).

Current registration and active binding are read from PostgreSQL. `connection_state` holds a lease under the per-EMS advisory transaction lock; an expired/new owner increments the numeric fence, a live renewal retains it. Database time determines expiry. Each ingress attempt and producer publish rechecks ownership. Consumers must recheck the envelope fence before domain processing; PG ownership and Kafka publication cannot form one atomic transaction.

Lane routing uses decoded wire type: normal EMS/cabinet/cell telemetry → fast; structure/current-alarm/heartbeat/status/response → state; important-history/alarm-event/alarm-data → reliable. EMS UUID is the Kafka key. The envelope retains raw body/topic, canonical content hash, decoded type/channel, immutable receivedAt, random ingressEpoch identity, numeric sequence and numeric fencingToken. The raw body contains protocol message identity (connectionId/seq/taskId/part/alarmId); downstream decoders must interpret it by type. Epoch UUIDs have no ordering meaning.

Three bounded queues and three single-completion pumps bound transport work. Kafka callbacks are explicitly limited to three; producer memory8MiB, max.block1s, delivery timeout10s, acks=all, idempotence enabled. Close rejects further work, resolves pending completions, clears queues, interrupts pumps, closes MQTT and producer. MQTT PUBACK acknowledges bounded transport acceptance only. The reliable actor commits canonical objects and deduplication in PostgreSQL before its transactional outbox publishes a business saved ACK. Conflicting content is quarantined without a success ACK. Fast telemetry may be lost during transport failure.

State/reliable consumers, connection fencing, read-only query dispatch (`structure.get`, `alarm.current.get`), ACK recovery and typed ClickHouse telemetry/reliable projection are implemented. ClickHouse configuration also requires `EMS_CH_HTTP_URL`, `EMS_CH_USER`, `EMS_CH_PASSWORD`. The strict MQTT plugin enforces verified single certificate CN, original ClientID equality and MQTT3.1.1. [Deployment instructions](../../docs/ems-integration/operations/2026-09-28-deployment/README.md) use a dedicated 8884 broker and map existing managed `EMS_DB_*` variables to worker `EMS_DATABASE_*` names without copying secrets.

Server-only `TransportLiveCheck` is a test entry point requiring an independent schema, temporary topics and server-held credentials. Controlled tests do not establish real EMS compatibility. Actual UUID/site/firmware admission, two-site reconnect/backfill/downlink checks, authenticated UI acceptance, 24-hour observed capacity and a formal write-control contract remain separate live acceptance requirements. Existing legacy MQTT8883 remains active and must be preserved.
