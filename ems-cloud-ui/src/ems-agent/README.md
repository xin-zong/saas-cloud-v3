# 一期 EMSAgent 迁移

源：用户提供的 `EMS-Cloud-Cabinet-Control-Platform-master/ruoyi-ui/src/components/FloatingBubble`。保留 `AssistantDialog.vue`、重设计 SCSS、加载动画、站点名称工具和原图标/头像资源。原项目许可证见 `legacy/LICENSE`。

独立 HTML `ems-agent.html` 由同一 Vite 构建产出，React 宿主仅在展开时加载；Vue、ElementUI、ECharts、PDF 依赖不会随主登录页初始化。官方构建插件参考 https://github.com/vitejs/vite-plugin-vue2 ，Vue 升为其要求的 2.7；插件的 peer 范围止于 Vite 7，本项目 Vite 8 的开发加载和生产构建需实际验证，不以 peer 声明替代验收。

适配边界：

- React 宿主接入实际 API 工作台及场站下钻；原 demo 工作台保留旧助手。
- iframe 通信限定同源、指定窗口和随机通道，不传登录令牌、密码或设备采样。站点 ID/名称从当前用户已有授权目录传入，旧若依目录和硬编码服务地址不进入请求链路。
- 本地模式、范围和会话按企业/用户隔离；一期原页面动作不会执行，返回明确未适配状态。没有替用户下发设备命令。
- 原版缩放、全屏、上下文、多选站点、时间范围、模式、历史、富文本、图表及报告渲染保留。只改资源引用、上下文与服务适配，未重新绘制助手布局。
- 纠正：一期 `.env.production` / `.env.staging` 已指定原 Agent 地址。原健康接口实际 200/ok、RAG ready，原密钥通过工具接口鉴权，工具数量 32；不是原 API 故障。上一轮只查开发环境，遗漏正式地址，误将前端替换为不可用适配器，本轮已恢复真实请求。
- 本地 `/ems-agent-api` 由 Vite 服务端代理到原 Agent。私有配置位于忽略目录且 ACL 限定当前用户和 SYSTEM；密钥不进入浏览器。代理先验证当前 API 登录和实际站点授权，验证会话/附件归属，强制 dry_run=true，替换客户端声称身份，不向原服务转发当前系统登录令牌。原页面动作仍禁用。
- 真实流式连接已通过页面发送测试消息并收到“连接成功”；不能据此声称所有业务工具、附件、图表和报告回包均已验收。原 Agent 查询的数据仍由原服务负责，本轮没有把其后端迁移到新库；新库场站与原服务站点编码及数据口径还需单独核对，不能把回复当作已完成新库业务对账。
- 本地服务重启后会话/附件归属内存表清空，原历史仅作本地回看，需新建会话或重新上传后继续；不放行未知资源 ID。
- 正式部署由 Nginx 将同源 `/ems-agent-api/` 转发到 Java `/api/agent/` 网关。沿用现有登录和站点权限，服务端保存原服务密钥并强制只读；V69 将会话及附件归属保存到独立新库，重启后仍可校验。流式响应禁用代理缓冲，限制大小、超时与资源归属。
- 默认提示和标签沿用一期原文；未声称已经完成全部中文化。

本地已通过真实连接验收。用户随后授权同步独立云端，采用服务端网关和独立新库归属表；发布结果以激活记录和实屏验收为准。39项定向测试通过（包括代理、UTF-8分块流、客户端、身份范围隔离及既有导航/登录回归）；类型检查与构建通过。不执行全局浏览器测试脚本。
